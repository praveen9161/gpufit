# Session C: GPUFit v0.1 on 4 real GPUs, straggler vs rescue (2026-10-02)

**GPUFit v0.1 worked end to end on real hardware, installed with its Helm chart:** observe mode
reported a degraded GPU without touching anything; one `helm upgrade` switched to enforce + rescue;
GPUFit then moved a running 2-GPU training job off the degraded GPU, and the job resumed from its
checkpoint on two healthy GPUs. **Rescue finished the job 14 s sooner than leaving it as a
straggler (987 s vs 1001 s).** The gain is small because this job was short; the measurements
give the break-even (below).

## Setup

- 4x AWS g5.xlarge (1x NVIDIA A10G each), us-east-1a, Deep Learning AMI (PyTorch 2.12, Ubuntu 24.04).
  About 70 min, **~$5.16**. Total real-GPU spend for the project: **~$8.5**.
- k3s v1.37.1 (server + 3 agents), NVIDIA's DRA driver (chart 0.5.0, DeviceClass `gpu.nvidia.com`).
- **GPUFit installed with `charts/gpufit`** (this repo's chart, image built from the same commit):
  agent reading the real `nvidia-smi` (window 30 s), demo timers degrade-after 20 s, recover-after
  60 s, rescue grace 30 s (production defaults: 5 min, 30 min, 2 min). Values: `helm-values.yaml`.
- Job: 2-pod PyTorch DDP Indexed Job, session B's synthetic model (134 M params, fp16), 400
  steps, checkpoint every 50 steps (1.1 GB: weights + SGD momentum) to a small HTTP store
  (`session-b/workloads/ckpt_store.py`). Opted in with `gpufit.io/rescue: "true"`, and a Job
  `podFailurePolicy` that ignores evictions.
- Degradation: at step 100, the power limit of one of the job's GPUs (node `ip-10-42-1-192`)
  300 -> **150 W** (`nvidia-smi -pl 150`), as in session B.

## Results

| Run | GPUFit | Placement | Job time | Extra vs healthy |
|---|---|---|---|---|
| R0 healthy | observe | -18, -192 | 901 s | - |
| R1 one GPU at 150 W | **observe** (reports only) | -18, -192 (stays) | 1001 s | **+100 s** |
| R2 one GPU at 150 W | **enforce + rescue** | -18, -192 -> **-144, -18** | 987 s | **+86 s** |

- Healthy: 2.25 s/step. Degraded (R1, after the power cut): 2.59 s/step -> **the job ran at 0.87**
  (session B measured 0.84 for the same setup).
- Every checkpoint stalls both GPUs ~10 s (8 per run, same in every run).

### Rescue timeline (R2), measured

| | |
|---|---|
| power cut -> node out of the training pool | 32 s (agent window + degrade-after 20 s) |
| -> job evicted | 36 s (rescue grace 30 s + one 5 s reconcile) |
| -> both pods running again on healthy GPUs | 22 s (Job recreates pods once the old ones are gone) |
| checkpoint load | 3.0 s |
| work redone (steps since the last checkpoint) | ~31 steps (~70 s) |

The new pods went to `-144` (the spare) and `-18` (the job's healthy GPU, freed by the eviction);
`-192` stayed out of training.

### The report vs the measurement

`kubectl gpufit report` after R1: job on a GPU scoring 50 for 12m45s, estimated waste **0.214
GPU-hours**. Measured: 100 s x 2 GPUs = **0.056 GPU-hours**. The estimate (speed = score/100)
is **3.8x too high** for this mild degradation, consistent with session B (score 50, real 0.84).
Calibrating the estimate with sessions B and C is follow-up work.

## What it means

- **Straggler cost grows with the job; rescue cost is fixed.** Here a straggler at 0.87 loses
  0.15 s per second of remaining work; the rescue cost ~86 s in total. *Estimate from these
  measurements:* rescue pays off when more than **~10 min** of work remains after the
  degradation (this job had ~11 min left, hence the narrow win). With production timers
  (degrade-after 5 min, grace 2 min) GPUFit waits ~6 min longer, but the job keeps running
  (degraded) meanwhile, so the fixed cost rises to ~141 s and the break-even to **~16 min**.
  Large training jobs run for hours, far past either.
- The redone work is bounded by the checkpoint interval (here ~113 s), so the checkpoint
  frequency, not GPUFit, sets most of the rescue cost.
- Not measured here: deeper degradations (thermal throttling, clock locks), more GPUs per job (a
  straggler slows every GPU in the job, so the loss rate grows with job size while the rescue
  cost doesn't), and a cluster with no spare GPU (the job would wait Pending).

## Problems found

1. `kubectl gpufit report` estimate too pessimistic (above).
2. `helm upgrade --reuse-values` turned the kind values' `nodeSelector: {nvidia.com/gpu.present: null}`
   into an empty label: the agent stopped running on kind (not on the real cluster, where nodes
   carry the label). Fixed: chart value `agent.gpuNodesOnly`.
3. The rehearsal on kind first counted evicted (still "Running", terminating) pods as the
   recreated ones, and degraded a GPU the job didn't hold (8 simulated GPUs per node). Both fixed
   before or after this session; they didn't affect the measurements above (the timeline fix
   was in place for the real run).
